# 项目会议安排（智学云 · 项目二）

> **配套文档**：`05-项目管理模板.md`（07 会议纪要模板）、`04-答辩PPT大纲.md`
> **考核依据**：实验指导书要求《华为项目管理模板》中「07 会议纪要」**不少于 4 次**，且待办需闭环
> **适用团队**：4 人组（PM / 前端 / 后端 / AI+测试）；人数不同时按角色合并，一人可兼两角
> **项目周期**：5 周。下表日期按 W1 = 2026-11-23（周一）起算，实际以团队日历为准

---

## 一、这份安排解决什么问题

开会最容易出的三个毛病：**没有议程、没有结论、没有跟进**。
本安排用三条硬约束对冲：

1. **每个会都有固定议程表**——照着走，不跑题
2. **每个议题必须有结论**——结论只有三种：通过 / 修改后通过 / 挂起并指定下次复议时间
3. **每条待办必须有人 + 有时间**——无责任人或无截止日的事项，当场作废重写

## 四、各次会议议程

### 4.1 项目启动会（W1 周一，60 min）— 必交纪要 ①

**目标**：一个会开完，所有人都知道"做什么、谁来做、什么时候交"。

| 时段 | 议题 | 主讲 | 产出 |
|---|---|---|---|
| 00–05 | 签到、会议目标与纪律说明 | PM | — |
| 05–15 | 解读实验指导书：交付物清单与评分点 | PM | 考核要点清单 |
| 15–25 | 选题确认与技术栈拍板（FastAPI + Vue3 + MySQL） | 全员 | 技术选型结论 |
| 25–40 | 角色分工与职责边界（谁对哪个模块的 Bug 负责） | PM | 01 项目组成员表 |
| 40–50 | **范围冻结**：P0 必做 / P1 争取 / P2 加分，逐条表决 | 全员 | 范围清单（签字确认） |
| 50–58 | 里程碑与下次会议时间（M1–M5） | PM | 04 进度计划表 |
| 58–60 | 待办认领与散会 | PM | 待办台账 |

**会前准备**：PM 提前 1 天把指导书考核点、候选技术栈发群；每人准备 3 分钟"我想做什么"。

**必须产出的 3 个结论**：① 技术栈定了 ② 分工定了 ③ 范围定了（不做什么也写进去）。

### 4.4 每日站会（每日，15 min）

**形式**：线上语音，站着开，**不开电脑、不现场改代码**。

每人固定说三句，超时打断：

1. 昨天完成了什么（对得上进度表的哪一条）
2. 今天要做什么（交付物是什么）
3. 有没有阻塞（需要谁配合）

**红线**：站会不解决问题。任何需要讨论超过 2 分钟的话题，记下来会后单独拉 2–3 人小会。

### 4.5 Sprint 评审会（W2/W3/W4 周日，60 min）— 必交纪要 ②③④

**会前 24 小时**：各责任人把可演示的版本合并到 `main`，PM 提前拉演示清单；演示不通过的功能不临时救场，直接记为缺陷。

| 时段 | 议题 | 主讲 | 产出 |
|---|---|---|---|
| 00–05 | 上轮待办闭环检查（逐条对台账） | PM | 闭环率 |
| 05–25 | **功能演示**（按主链路顺序，边演示边说验收点） | 各责任人 | 演示记录 |
| 25–35 | 缺陷与体验问题登记（当场分级 P0/P1/P2） | 测试 | 缺陷清单 |
| 35–50 | 下个 Sprint 任务拆解与主动认领 | 全员 | 任务表（人 + 截止） |
| 50–58 | 风险识别与应对（每条风险必须配对策 + 责任人） | PM | 风险台账 |
| 58–60 | 结论确认与散会 | PM | 纪要 ④ |

**演示纪律**：演示失败不解释、不辩解，只记问题。解释放到缺陷分析环节。

**三轮评审的关注重点**：

| 轮次 | 演示范围 | 必须要问的问题 |

### 4.8 项目复盘会（答辩后，45 min）

三个问题，每人轮流回答，记录人逐条记录：

1. **做对了什么**（可复用的做法，写进下次项目清单）
2. **做错了什么**（不追责，只找机制原因）
3. **下次改什么**（具体到可执行的一条）

产出：复盘报告（1 页），作为个人实践报告的素材。

## 五、会议运行规则（6 条，建议写进团队公约）

1. **提前 10 分钟发议程**：无议程不开会，临时会也要在群里发三条要点。
2. **准时开始**：到点即开，不等迟到者；迟到者自行看纪要。
3. **一议题一结论**：结论三选一——通过 / 修改后通过 / 挂起（挂起必须定时复议）。
4. **纪要 24 小时内发出**：谁主持谁定稿，谁记录谁执笔，发群 + 存档 `docs/`。
5. **待办必须"有人有日"**：无责任人、无截止日的事项不得进入待办表。
6. **决议可追溯**：涉及范围、技术选型、接口变更的决议，必须在纪要里写明"谁提出、谁反对、最终如何定"。

## 七、会议纪要与指导书要求的对应关系

按 `05-项目管理模板.md` 的「07 会议纪要模板」填写，**5 次纪要的必填差异**如下：

| 纪要 | 会议 | 必须写实的字段 | 老师最可能核查的点 |
|---|---|---|---|
| ① | 项目启动会 | 参会人员、分工决议、范围冻结清单 | 分工是否与 01 成员表一致 |
| ② | Sprint1 评审 | 演示了什么、发现几个缺陷、谁修 | 缺陷是否真被修复（对得上 Git 提交） |
| ③ | Sprint2 评审 | 主链路是否走通、范围有无变更 | 变更是否有理由和对策 |
| ④ | Sprint3 评审 | AI 四功能演示结果、Mock 降级确认 | 答辩演示与纪要描述是否一致 |
| ⑤ | 答辩准备会 | PPT 分工、问答责任表、环境核查结果 | 团队是否真的演练过 |

**填写红线**（缺口清单 D6 已标注）：

- 日期、议题、结论必须与项目真实进展吻合，**不得直接提交模板里的示例内容**
- 每条待办要有最终状态（完成 / 取消 / 转下轮），不能全是空白
- 记录人与主持人不能是同一人（体现分工）

## 九、开会常见问题处理

| 现象 | 处理办法 |
|---|---|
| 讨论跑题、越聊越远 | 主持人一句话拉回："这个记下来单聊，现在回到第 3 项议题" |
| 两人争执不下 | 限时 3 分钟，超时由主持人裁决，异议记入纪要"保留意见" |
| 有人长期缺席 | 缺席者次日必须在群里补看纪要并回执待办；连续 2 次缺席由 PM 单独沟通 |
| 演示翻车 | 不救场、不解释，记缺陷，会后单独复盘 |
| 会议开成"汇报会" | 站会只讲事实不讲过程；评审会只讲演示不讲代码 |
| 纪要没人看 | 每次会前 5 分钟先过上次待办，未闭环的当场追问 |
